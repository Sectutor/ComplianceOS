Why AI agents need a separate compliance checklist

A standard compliance checklist assumes a human-in-the-loop operating a software tool. AI agents break that assumption.

When an agent has:

  • File system access
  • Code execution capabilities
  • Autonomous decision-making
  • Plugin and tool invocation
  • Persistent memory across sessions

…your compliance model shifts from "did the user follow procedure?" to "did the agent operate within its sandboxed constraints?"

"An LLM without guardrails is not a tool. It's an employee with no training, no manager, and root access to your production database." — Industry axiom

The key difference: traditional compliance looks at organizational policies and human behavior. AI agent compliance looks at runtime permissions, input validation, session isolation, and model behavior — because the agent is the operator.

1. OWASP LLM Top 10 — The model layer

These controls apply to every agent that sends prompts to a language model. Even if you're using a managed API like OpenAI or Anthropic, these vulnerabilities exist at the application layer — your responsibility.

LLM01: Prompt Injection

Do you have input sanitization or guardrails to prevent prompt injection attacks on your LLM?

This is the #1 risk for any LLM-powered agent. An attacker crafts input that overrides the system prompt. The fix: input scanning, role separation, and protect_first_system flags.

LLM02: Insecure Output Handling

Do you validate and sanitize LLM outputs before rendering them downstream?

If your agent's output feeds into a terminal command, a database query, or a frontend — and you don't sanitize — you've created an injection vector.

LLM03–LLM10: The full list

Training data poisoning, denial of service, supply chain vulnerabilities, sensitive information disclosure, insecure plugin design, excessive agency, overreliance, and model theft.

2. OWASP Agentic Security Index — The agent layer

Where the LLM Top 10 covers the model, the Agentic Security Index covers the agent itself — its tools, permissions, memory, and execution environment.

These controls apply if your agent can execute code, access files, call APIs, or install plugins. If you're running a self-hosted agent (Hermes, OpenCLAW, AutoGPT) or a multi-agent framework (CrewAI, LangGraph, AutoGen), these are critical.

"The difference between a chatbot vulnerability and an agent vulnerability is action. A chatbot can leak data. An agent can delete it." — OWASP ASI Working Group

Scoped by agent type:

  • API-only agents (OpenAI, Claude, Copilot): ASI controls generally don't apply — the provider handles the sandbox.
  • Framework agents (LangChain, CrewAI, AutoGen): ASI controls apply because you control the execution environment.
  • Self-hosted agents (Hermes, OpenCLAW, Custom): All ASI controls apply.

3. NIST AI RMF — The governance layer

The NIST AI Risk Management Framework is the gold standard for organizational AI governance. It's framework-agnostic — it doesn't prescribe specific controls, but tells you how to govern AI risk.

Four functions: Govern, Map, Measure, Manage. Our checklist maps 23 subcategories into actionable yes/no questions.

Example: "Does your organization have documented policies and procedures for AI risk management across the system lifecycle?" (GOV-1)

These apply to every organization deploying AI, regardless of agent type.

4. EU AI Act — The regulatory layer

The EU AI Act classifies AI systems by risk level: Unacceptable, High, Limited, Minimal. If your agent makes decisions about hiring, credit, healthcare, or access to services, it's likely high-risk.

High-risk systems must comply with 13 requirements covering:

  • Risk management system (Art. 9)
  • Data governance (Art. 10)
  • Technical documentation (Art. 11)
  • Automatic logging (Art. 12)
  • Transparency (Art. 13)
  • Human oversight (Art. 14)
  • Accuracy, robustness, cybersecurity (Art. 15)
  • Conformity assessment (Art. 16)
  • Fundamental rights impact assessment (Art. 53)
  • Post-market monitoring (Art. 72)
